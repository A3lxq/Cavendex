# Exact, pinned, hash-verified dependency closure of requirements.txt.
# `pip install --require-hashes -r requirements.lock.txt` (see
# DEPLOYMENT.md) refuses to install anything whose downloaded
# wheel/sdist doesn't match the SHA-256 recorded here — version-pinning
# alone stops "a newer, unaudited release got silently pulled in," but
# says nothing about the *exact bytes* installed actually matching what
# was audited; a compromised index/mirror or a MITM'd download could
# still swap in a different (same-version) artifact without this.
#
# Regenerate with:
#   python3 -m venv /tmp/lockgen && /tmp/lockgen/bin/pip install -r requirements.txt \
#     && /tmp/lockgen/bin/pip freeze > requirements.lock.txt && rm -rf /tmp/lockgen
# (a fresh, throwaway venv, never the dev venv you're working in — this
# venv may have pip-audit or other tooling installed that would otherwise
# leak into the lock file). requirements.txt itself stays >=-pinned for
# development flexibility; use this file for production installs so a
# `pip install` can't silently pull a newer, unaudited version.
#
# Then add the --hash entries (pip itself has no built-in "generate
# hashes for a lock file" command):
#   pip download --no-deps -r requirements.lock.txt -d /tmp/wheels
#   # for each `pkg==version` line, compute sha256 of its downloaded
#   # wheel/sdist in /tmp/wheels and append " \\\n    --hash=sha256:<hex>"
# If you have pip-tools installed, `pip-compile --generate-hashes` does
# both steps (resolve + hash) in one command and is the recommended path
# going forward — this file just wasn't generated with it since pip-tools
# wasn't available in the environment that produced it.
#
# Verify installability after regenerating:
#   python3 -m venv /tmp/hashcheck && /tmp/hashcheck/bin/pip install \
#     --require-hashes -r requirements.lock.txt && rm -rf /tmp/hashcheck
#
# Re-run `pip-audit -r requirements.lock.txt` after every regeneration.
#
# IMPORTANT: this file is tied to the exact Python interpreter it was
# generated against (currently 3.14), not just the pinned versions. A
# compiled-extension package (aiohttp, etc.) ships a separate wheel per
# Python version, each with its own legitimate hash — installing this
# file under a *different* interpreter will correctly fail
# --require-hashes on a real, non-tampered wheel (confirmed live: it
# happened when Cavendex's own Dockerfile briefly used python:3.12-slim
# against this 3.14-generated file). Regenerate from a matching
# interpreter — including in the verify step above — if you ever target
# a different Python version, and keep any Dockerfile's base image
# version in sync with whatever this file is actually generated
# against.
